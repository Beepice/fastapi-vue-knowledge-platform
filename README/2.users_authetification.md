# Users & Authentication 模块说明

> 描述用户注册、登录、JWT 鉴权认证的实现机制。
> 涉及路由：`/api/users/login`、`/api/users`（register）、`/api/users`（当前用户）

---

## 1. 模块职责

| 子功能 | 路由 | 方法 |
|--------|------|------|
| 用户登录 | `/api/users/login` | POST |
| 用户注册 | `/api/users` | POST |
| 获取当前用户 | `/api/users` | GET |
| 更新当前用户 | `/api/users` | PUT（注释中，未启用） |

**核心职责**：
- 用户注册时加密存储密码
- 登录时校验密码并签发 JWT
- 受保护接口通过 JWT 自动鉴权

## 3. 用户注册流程

### 3.1 接口定义

**请求**：
```
POST /api/users
Content-Type: application/json

{
    "user": {
        "username": "testuser",
        "email": "test@example.com",
        "password": "mypassword"
    }
}
```

**响应**：
```
201 Created
{
    "user": {
        "username": "testuser",
        "email": "test@example.com",
        "bio": "",
        "image": null,
        "token": "eyJhbGciOiJIUzI1..."
    }
}
```

### 3.2 链路

```
客户端 POST /api/users
    ↓
Pydantic 校验（UserInCreate）
    ↓
1. check_username_is_taken() → 400 USERNAME_TAKEN
2. check_email_is_taken()    → 400 EMAIL_TAKEN
    ↓
users_repo.create_user()  （密码在仓储层自动加 salt + bcrypt）
    ↓
jwt.create_access_token_for_user(user, SECRET_KEY)
    ↓
返回 UserInResponse（带 token）
```

### 3.3 密码存储机制

**存储结构**：

| 字段 | 内容 | 说明 |
|------|------|------|
| `salt` | 自定义 salt（**明文存储**） | 用于增加密码哈希的随机性 |
| `hashed_password` | bcrypt 哈希输出 | 不可逆，bcrypt 内部已含随机 salt |

**校验流程**：
```
用户输入密码
    ↓
从 DB 读 salt（明文）
    ↓
拼接：salt + password
    ↓
bcrypt 校验 → True / False
```

**bcrypt 特性**：
- **单向哈希**：不可逆，无法从 hash 反推明文
- **内嵌 salt**：hash 输出里已含 bcrypt 自带的随机 salt
- **相同密码，每次 hash 结果不同**：salt 每次自动生成随机值

**自定义 salt 的作用**：

| 方案 | 攻击成本 |
|------|---------|
| 明文直接 bcrypt（无 salt） | 一次计算可批量比对所有用户 |
| bcrypt 自带 salt | 每个用户 salt 不同，但仍可逐用户跑字典攻击 |
| 项目方案（自定义 salt + bcrypt） | 同上，计算次数相同；价值在于让"同密码用户的 hash 更分散" |

**核心作用**：让相同密码的用户哈希值不同，攻击成本从 M 次增加到 N×M 次（批量攻击需逐用户分别计算）。

### 3.4 可能的问题

| 问题 | 现象 | 原因 | 解法 |
|------|------|------|------|
| 注册时报 `password cannot be longer than 72 bytes` | bcrypt 报错 | 输入超过 72 字节限制 | 前端限制密码 ≤ 64 字符 |
| 注册后无法登录 | 密码"正确"但校验失败 | salt 没存或存错字段 | 检查 users 表 salt 列是否有值 |
| 邮箱已注册但提示用户名重复 | 错误信息不匹配 | 检查顺序反了 | 先检查 username 再检查 email |

## 4. 用户登录流程

### 4.1 接口定义

**请求**：
```
POST /api/users/login
Content-Type: application/json

{
    "user": {
        "email": "test@example.com",
        "password": "mypassword"
    }
}
```

**响应**：
```
200 OK
{
    "user": {
        "username": "testuser",
        "email": "test@example.com",
        "bio": "",
        "image": null,
        "token": "eyJhbGciOiJIUzI1..."
    }
}
```

错误响应（统一）：
```
400 Bad Request
{"detail": "INCORRECT_LOGIN_INPUT"}
```

### 4.2 链路

```
客户端 POST /api/users/login
    ↓
1. users_repo.get_user_by_email(email)
   ├─ 用户不存在 → 捕获异常 → 抛 400 INCORRECT_LOGIN_INPUT
   └─ 用户存在 → 继续
    ↓
2. user.check_password(password)
   ├─ 校验失败 → 抛 400 INCORRECT_LOGIN_INPUT
   └─ 校验成功 → 继续
    ↓
jwt.create_access_token_for_user(user, SECRET_KEY)
    ↓
返回 UserInResponse（带新 token）
```

### 4.3 统一错误信息设计

用户不存在和密码错误**返回相同的错误信息**（INCORRECT_LOGIN_INPUT）。

**目的**：防止攻击者通过不同错误信息**枚举哪些邮箱已注册**。

### 4.4 可能的问题

| 问题 | 现象 | 原因 | 解法 |
|------|------|------|------|
| 登录后 token 立即失效 | 刚登录成功，下次请求就 403 | 签发和验证的 SECRET_KEY 不一致 | 确认 .env 里 JWT_SECRET_KEY 一致 |

## 5. JWT 鉴权认证

### 5.1 Token 签发

**Token Payload 结构**：
```json
{
    "username": "testuser",
    "exp": 1735689600,
    "sub": "access"
}
```

**字段说明**：

| 字段 | 含义 | 备注 |
|------|------|------|
| `username` | 用户标识 | 业务字段 |
| `exp` | 过期时间 | decode 时自动检查，过期则抛异常 |
| `sub` | token 类型 | 固定值 "access" |

**Token 编码结构**：
```
Header.Payload.Signature
  ↓        ↓       ↓
base64编码   base64编码   HMAC-SHA256(Header.Payload, SECRET_KEY)
(alg+typ)   (username+exp+sub)
```

**关键特性**：
- Header 和 Payload 是 base64 编码，**任何人都能解码看到内容**（不是加密）
- Signature 用 SECRET_KEY 签名，防篡改：攻击者改了 Payload，签名就对不上

### 5.2 鉴权依赖链

```
客户端请求：Authorization: Bearer eyJhbGciOiJIUzI1...
    ↓
RWAPIKeyHeader 解析 Authorization 头
    ├─ 缺失 → 403 AUTHENTICATION_REQUIRED
    └─ 提取出 token 字符串
    ↓
验证 Bearer 前缀
    ├─ 前缀错误 → 403 WRONG_TOKEN_PREFIX
    └─ 前缀正确 → 返回 token
    ↓
jwt.decode(token, SECRET_KEY)
    ├─ 签名错误 → 403 MALFORMED_PAYLOAD
    ├─ 已过期 → 403 MALFORMED_PAYLOAD（PyJWT 自动检查 exp）
    └─ 正常 → 返回 username
    ↓
users_repo.get_user_by_username(username)
    ├─ 不存在 → 403 MALFORMED_PAYLOAD
    └─ 存在 → 返回 User 对象
    ↓
User 对象注入到路由函数参数
```

**过期机制**：
- encode 时主动塞 exp（当前时间 + 7 天）
- decode 时 PyJWT 自动检查 exp（无需业务代码显式判断）
- 过期 → 抛 ExpiredSignatureError → 被捕获 → 403

### 5.3 在路由中使用

```python
# 必须登录的接口
user: User = Depends(get_current_user_authorizer(required=True))
# 无 token → 403 AUTHENTICATION_REQUIRED

# 可选登录的接口
user: Optional[User] = Depends(get_current_user_authorizer(required=False))
# 无 token → user = None
```

### 5.4 可能的问题

| 问题 | 现象 | 原因 | 解法 |
|------|------|------|------|
| 所有受保护接口 403 | 提示 `AUTHENTICATION_REQUIRED` | 请求头没有 `Authorization: Bearer xxx` | 前端 axios 拦截器未注入 token |
| Token 解析失败 | `MALFORMED_PAYLOAD` | Token 被篡改或过期 | 用户重新登录 |

| 字段 | 作用 | 示例 |
|------|------|------|

## 7. 安全设计要点

### 7.1 密码安全

| 措施 | 说明 |
|------|------|
| 密码加 salt | 每个用户独立自定义 salt |
| 单向哈希 | bcrypt（不可逆） |
| 响应不泄露 | `UserInResponse` 无 `hashed_password` 字段 |
| 统一错误信息 | 登录失败不区分"邮箱不存在"和"密码错误" |

### 7.2 Token 安全

| 措施 | 说明 |
|------|------|
| 签名校验 | HS256 + SECRET_KEY，防伪造 |
| 过期机制 | 7 天，PyJWT decode 自动检查 |
| 前缀校验 | 必须 `Bearer xxx`，否则 403 |

### 7.3 接口状态码

| 状态 | HTTP 码 | 错误信息 |
|------|--------|---------|
| 成功 | 200/201 | — |
| 缺 token | 403 | `AUTHENTICATION_REQUIRED` |
| token 无效 | 403 | `MALFORMED_PAYLOAD` |
| token 前缀错 | 403 | `WRONG_TOKEN_PREFIX` |
| 登录失败 | 400 | `INCORRECT_LOGIN_INPUT`（统一） |
| 用户名占用 | 400 | `USERNAME_TAKEN` |
| 邮箱占用 | 400 | `EMAIL_TAKEN` |
